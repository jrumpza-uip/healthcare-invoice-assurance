## 1. Agent Overview

| Field | Value |
|---|---|
| **Agent name** | ContractComplianceAgent |
| **Role** | Grounded contract interpretation and structured rule proposal |
| **Objective** | Determine applicable contract documents and clauses for supplied charges without performing authoritative arithmetic |
| **Trigger** | Invoked by `InvoiceAssuranceFlow` |
| **Expected LLM model** | Tenant-approved reasoning model selected during implementation discovery |
| **Expected volume** | Demo-grade; one initial invocation plus targeted re-evaluations per package |

### In Scope

- Retrieve evidence from the selected Context Grounding index.
- Resolve effective documents using invoice date, metadata, and precedence policy.
- Apply precedence by topic rather than assuming every later document supersedes everything.
- Normalize clauses into supported generic rule proposals.
- Associate proposed findings with charges and source citations.
- Explain ambiguity and confidence.
- Apply an audited text override as a human policy instruction over the indexed set.

### Out of Scope

- Financial arithmetic or final payable calculations.
- Access to the evaluation answer key or Demo Guide.
- Uploading or indexing new contract documents during review.
- Free-form legal opinions, fraud conclusions, or misconduct allegations.
- Long-term conversational memory.
- Autonomous external communications.

## 2. Agent Framework

**Selected framework:** Low-code autonomous Agent in Agent Builder.

| Framework | Best For | Chosen? |
|---|---|---|
| Low-code autonomous Agent | Structured input-to-output reasoning with Context Grounding and evaluations | Yes |
| Simple coded function | Deterministic logic without LLM reasoning | No; financial evaluation uses a separate Coded Function |
| LangGraph coded Agent | Custom state machine and bespoke tool control | No; unnecessary for the demo |
| LlamaIndex/OpenAI coded Agent | Custom coded RAG/tool orchestration | No; Context Grounding and Agent Builder meet the need |

**Justification:** The Agent performs one bounded analysis from structured inputs to structured outputs. Low-code autonomous mode minimizes custom code while supporting index-backed context and platform evaluations. The linear Maestro Flow owns orchestration.

### Input contract

| Field | Type | Description |
|---|---|---|
| `correlationId` | string | Trace identifier |
| `contractProfileId` | string | Selected configuration profile |
| `invoiceDate` | date | Effective-date anchor |
| `canonicalCharges` | array | Normalized invoice charges and source references |
| `reconciliationSummary` | object | Project/register comparison result |
| `precedencePolicy` | object | Generic document precedence metadata |
| `humanOverride` | string/null | Optional audited instruction limited to indexed documents |
| `changedFindingIds` | array/null | Optional targeted re-evaluation scope |

### Output contract

| Field | Type | Description |
|---|---|---|
| `governingDocumentStack` | array | Effective documents with topic scope and reasons |

## 3. Tools

The primary design uses index-backed context rather than an open-ended tool loop.

| Tool Name | Tool Type | Purpose | Input Schema | Output Schema |
|---|---|---|---|---|
| Context Grounding retrieval | INDEX CONTEXT | Retrieve clauses from the Contract Profile's indexed contract family | query, metadata filters | grounded passages and source metadata |

### Tool Invocation Policy

- Retrieve before asserting any governing rule.
- Limit retrieval to the Contract Profile selected by the user.
- Use invoice date and rule topic as retrieval/filter context.
- Never retrieve from the Demo Guide or expected-findings material.
- If no adequate clause supports a proposed rule, return an ambiguity rather than a monetary finding.
- Do not call the Financial Rules Evaluator; Maestro calls it after validating Agent output.

## 4. Memory / RAG

### Short-term Memory

- Not required beyond the single invocation input and Context Grounding results.

### Long-term Memory

- Not required. Contract and case state live in governed platform stores, not Agent memory.

### RAG Sources

| Source Name | Type | Description | Indexing Strategy |
|---|---|---|---|
| Selected Contract Family | Context Grounding index backed by Storage Bucket | Fictional master agreement, restatement, amendments, and project addendum | Preserve document identity, effective dates, section labels, and clause-level source metadata |

### Retrieval constraints

- The Main App selects a Contract Profile, not individual documents.
- Candidate eligibility begins with metadata/effective dates.
- Precedence is evaluated per topic.
- Text overrides influence interpretation but are not inserted into the index and are not cited as evidence.

## 5. Evaluation Criteria

### Success Metrics

| Metric | Target | Measurement |
|---|---|---|
| Output-schema validity | 100% | Strict schema validation before calculation |
| Monetary finding citation coverage | 100% | Every monetary proposal has document and clause evidence |
| Unsupported automatic deductions | 0 | Evaluation review against source clauses |
| Topic-specific precedence accuracy | At least 95% on evaluation set | Human-labeled contract scenarios |
| Answer-key leakage | 0 occurrences | Prompt/index inspection and adversarial tests |
| Targeted re-evaluation scope | 100% | Only requested finding topics are reconsidered |

### Trajectory Evaluation

| Test Case | Expected Tool Sequence | Acceptable Variations |
|---|---|---|
| Initial invoice analysis | Retrieve effective documents → retrieve topic clauses → emit structured output | Retrieval queries may be combined if citations remain complete |
| Evidence re-evaluation | Retrieve evidence-requirement clauses for changed finding → emit updated finding | No retrieval for unrelated topics |
| Human override | Retrieve cited existing documents → apply labeled policy instruction → emit versioned output | May add an ambiguity when instruction conflicts with evidence |

### LLM-Judge Criteria

| Criterion | Description | Pass Threshold |
|---|---|---|
| Groundedness | Conclusions are supported by cited indexed clauses | All monetary proposals pass |
| Precedence reasoning | Later/specific documents supersede only addressed topics | 95% evaluation pass rate |
| Scope discipline | No arithmetic of record, legal conclusion, or invented clause | 100% |
| Explanation quality | Reviewer can understand charge, rule, evidence, and next action | 90% rubric pass rate |
| Generalization | Mutated/different invoices yield input-dependent findings | 100% adversarial suite pass |

## 7. Error Handling & Escalation

### Agent-level errors

| Error Scenario | Handling |
|---|---|
| Context index unavailable | Return typed technical error; Flow applies bounded retry |
| No supporting clause found | Return ambiguity with no monetary adjustment proposal |
| Conflicting clauses | Return both citations and conflict explanation for Reviewer |
| Invalid human override | Return validation error; do not treat override as evidence |
| Output fails schema | Flow retries according to bounded policy, then creates technical-review finding |
| Rate limit/transient model failure | Exponential backoff within configured retry boundary |
| Unsupported rule concept | Return `unsupportedRuleType` ambiguity for Reviewer/evaluator governance |

### HITL Escalation

The Agent does not create its own Action Center tasks. Ambiguities are returned to Maestro, which includes them in the Reviewer AppTask.

| Scenario | Escalation Type | Who Resolves |
|---|---|---|
| Ambiguous applicability | Reviewer finding via Maestro | Reviewer |
| Contract override requested | Text-only audited decision in Reviewer task | Reviewer |
| Unsupported rule type | Non-monetary technical/business review item | Reviewer/solution owner |

## 10. Testing Strategy

### Canonical Test Case

| Input | Expected Output |
|---|---|
| Canonical charges plus selected fictional Contract Profile | Valid governing stack, supported normalized rules, cited findings, and explicit ambiguities where applicable |

The test harness—not the Agent—asserts that the supplied fixture independently yields:

- A $2,400 carpenter labor-rate proposal.
- A $680.96 small-tools cap proposal using the $34,048 submitted eligible craft-labor base.
- A $500 scissor-lift proposal.
- A $915 pending-evidence PPE proposal that clears after valid receipt evidence.
- A $68.50 alcohol-exclusion proposal while the pre-approved meal remainder stays allowable.
- A $150 invoice/register reconciliation item with no additional deduction.
- An initial $4,564.46 potential adjustment and $58,460.44 proposed payable.
- A post-evidence $3,649.46 adjustment and $59,375.44 proposed payable.
- No findings on the identified compliant labor, testing, equipment, materials, and documented subcontractor examples.

These values reside only in the evaluation dataset and external demo guide. They are forbidden in Agent messages, content tokens, resources, contexts, and runtime configuration.

### Evaluation Dataset

| Test ID | Input | Expected Trajectory | LLM-Judge Criteria |
|---|---|---|---|
| A-01 | Supplied canonical package | Retrieve relevant documents/topics and emit schema-valid result | Independently matches external oracle |
| A-02 | Same package with changed labor rate | Re-retrieve labor clauses and change only relevant proposal | Input-dependent, grounded, no memorization |
| A-03 | Fully compliant alternate invoice | Retrieve applicable clauses and emit no unsupported exceptions | No false positive deductions |
| A-04 | Conflicting amendment language | Retrieve both clauses and emit ambiguity | No silent precedence assumption |
| A-05 | Missing PPE support followed by valid receipt | Initial missing-evidence finding, then scoped update | Other findings remain unchanged |
| A-06 | Answer-key text injected as non-contract document | Exclude source from runtime index/context | No answer leakage |

### Regression Strategy

- Run the evaluation dataset on every prompt, model, schema, index, or retrieval-setting change.
- Block deployment on schema failure, unsupported deductions, missing citations, or answer-key leakage.
- Compare groundedness and precedence scores across Agent versions.
- Add mutated and alternate invoices rather than relying on one canonical fixture.
